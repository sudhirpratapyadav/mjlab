# CHORD -> mjlab Port Feasibility

## 1. Verdict

**A wholesale port is not possible today, and will never be a "port" — only a reimplementation.** The dominant blocker is that CHORD's entire Robotic Grounding stage (retargeting, Isaac Lab envs, rewards, wrench extraction, RL training) is a README-only stub in `github.com/nvidia-isaac/video_to_data` ("will be published in a later release"), and zero task data, trajectories, or checkpoints are downloadable anywhere (Probe 1). Even in the best future case where NVIDIA releases everything, the teacher checkpoints would not transfer (PhysX→MuJoCo dexterous-manipulation zero-shot transfer has no published success; quantified replay degradation of 15–56% across the boundary, Probe 4d), and three of seven upstream datasets (ARCTIC, GRAB, H2O) forbid redistribution of derived data (Probe 2). What *is* feasible: reimplement the CHORD recipe in mjlab from the paper's fully-specified rewards and rebuild teachers per task from upstream mocap — a months-scale effort at N=1831, or a weeks-scale effort for a curated subset.

## 3. The realistic path

**Stage 0 — calibration spike (days).** Measure mjlab per-task fixed overhead with `benchmark_smoke --isolate` (each task must run in its own subprocess; warp JIT cold-compile dominates first run; warm-cache expect O(10 s–1 min)/task — Probe 3.1). At N=1800 that is ~5–30 h of pure overhead across the sweep: real but small versus training. Import SharpaWave from Menagerie or reuse LEAP (Class C floating hand, 22-D actions, already tuned in-repo).

**Stage 1 — pipeline reimplementation (2–4 wk).** (i) Extend `MotionLoader`/`MotionCommand` from `tasks/tracking/` to the manipulation scene and add **object**-trajectory tracking (currently robot-bodies-only, Probe 3.4). (ii) Imitation reward = existing exp-kernel terms re-pointed at retargeted references. (iii) Wrench-guidance reward from the paper's formulas using `ContactSensorCfg` pos/force/normal (mind `contact_sensor_maxmatch`); DexMachina as design donor. (iv) Build the mesh importer (URDF→MJCF + CoACD) — the single largest missing infrastructure piece.

**Stage 2 — retargeting + task selection (1 wk).** Start **single-hand LEAP** on ungated permissive data (TACO CC-BY, then OakInk2/DexYCB); bimanual Sharpa second — mjlab supports two-entity scenes and concatenated 44-D action terms, but no bimanual config exists and every obs/reward term must be duplicated per hand (config work, Probe 3.5). ARCTIC/GRAB/H2O require registration and can never ship as data — scripts-only release pattern (Probe 2).

**Stage 3 — teacher training at scale.** No published per-task compute exists; parameterize as **N × T GPU-hours**. Plausible band from 4096-env PPO on dexterous tracking: T ≈ 1–4 GPU-h/task on A100. Then N=1831 → **~1,800–7,300 GPU-h ≈ 10–40 days on one 8×A100 node** at 100% success on the first attempt — realistically 1.5–2× with retries. N=100 (curated) → 100–400 GPU-h: a week of background queue on the shared cluster. Calibrate T in Stage 0 before committing.

**Stage 4 — distillation contract.** The continual-distill student demands one fixed `obs_dim` and one shared `action_dim` across all tasks; no padding/masking exists (Probe 3.6). CHORD-style per-task objects force a design decision **at dataset-extraction time**: fixed-size object-state slots zero-padded to a max-objects layout (cheap, fits existing code) vs. a per-task encoder (framework work). Single embodiment class per student keeps `action_dim` uniform; mixing single-hand and bimanual tasks in one student is off the table without action-head padding. Teachers drop into the existing `teacher.pkl`/`data.pkl` format as long as they are feedforward MLP Gaussians (Probe 3.7).

## 4. Should the user do it?

**Not wholesale.** The user's research question is replay-free continual learning over tasks with *distinct motion profiles*, and they already hold a 66-profile catalog. CHORD's 1,831 tasks are one-clip-per-task instances — under the user's counting rule this is instance-scale, not profile-scale: hundreds of clips share the same verb/contact structure and add per-instance variation, not new profiles. Spending ~2–7k GPU-hours plus 1–2 months of engineering to reproduce all 1,831 would buy mostly redundant profiles, on data that is partly unredistributable (ARCTIC/GRAB/H2O) and partly unobtainable (in-house videos).

**What maximizes research value per GPU-hour:** adopt CHORD as a *teacher factory recipe*, not a benchmark.
1. **Port the recipe** (object tracking + imitation + wrench rewards + 15 cm/40° success) into mjlab once — it upgrades the existing scripted/PPO teacher pipeline to demo-guided teachers for any future task.
2. **Curate a per-verb subset**: ~20–60 clips chosen for *distinct* motion/contact profiles (e.g. from TACO's tool-use verbs and OakInk2's bimanual affordances) as new Class C (floating LEAP) and, later, bimanual profiles extending the 66-profile catalog. That is 50–250 GPU-h of teacher training — one week of cluster background load — and every task is legally redistributable (TACO/OakInk2 permit derived data).
3. Skip: Sharpa embodiment swap (LEAP is already tuned in-repo and dex-retargeting supports it), checkpoint conversion (nothing to convert), and MPI/ETH-derived subsets until the recipe is proven.

**1–2 week spike, explicit success criteria:**
- Pick 5 TACO clips (CC-BY, ungated) with distinct verbs; retarget to LEAP via dex-retargeting.
- Implement object-trajectory tracking command + imitation reward on the Class C floating LEAP; **defer the wrench term** (paper's ablation subject, not needed to prove the pipeline).
- Train one PPO teacher per clip at 4096 envs; extract `teacher.pkl`/`data.pkl` with zero-padded object slots.
- **Success = (a)** ≥3/5 teachers reach completion ratio > 0.7 under the CHORD criterion; **(b)** measured T ≤ 4 GPU-h/task warm-cache including compile/capture overhead; **(c)** one teacher distills into the existing student alongside a current Class C task without obs-contract changes beyond padding.
- If (a) fails without wrench guidance, add the wrench reward (DexMachina donor) before scaling; if (b) fails, the curated-subset plan needs re-costing before any talk of hundreds of tasks.
